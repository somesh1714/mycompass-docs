1. Where this fits

The backend already has a fully built and tested auth system (see auth/jwt-google-signin.html and the 15 passing tests in AuthServiceTest): register, login, email verification, and forgot/reset password, all returning a stateless app JWT. This plan is the frontend that consumes exactly those five endpoints — nothing more, nothing speculative. Task/Project/Category UI is intentionally out of scope here since those backend domains don't exist yet (per the domain doc's own staged approach).

2. Backend prerequisite — CORS ACTION NEEDED

This must be added to the backend before any frontend page can call it. I checked SecurityConfig.java directly — there is currently no CORS configuration at all. Spring Security blocks cross-origin requests by default, and the React dev server (localhost:5173) and the backend (localhost:8080) are different origins from a browser's point of view. Without this, every fetch from the frontend will fail in the browser console with a CORS error, even though the same request works fine from curl (curl doesn't enforce CORS — only browsers do, which is exactly why our backend testing so far never surfaced this gap).

The fix is small — a CorsConfigurationSource bean allowing http://localhost:5173, wired into the existing SecurityFilterChain via .cors(...). This is a backend change, tracked here so it isn't forgotten, and should be the very first implementation step once this plan is approved.

7. State & data layer

AuthContext

A React context holding { user, token } in component state (memory only, lost on refresh — an accepted MVP tradeoff, same as documented in the auth plan). Exposes login(authResponse) (called after a successful login/register API response) and logout() (clears state, redirects to /login).

axios instance + interceptor

// api/client.ts
const client = axios.create({ baseURL: import.meta.env.VITE_API_BASE_URL });

client.interceptors.request.use((config) => {
  const token = getTokenFromAuthContext();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

client.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) logout(); // token expired/invalid → force re-login
    return Promise.reject(error);
  }
);

TanStack Query

Each API call (register, login, verify-email, etc.) is wrapped as a useMutation — gives you isPending/isError/error states for free, which map directly onto MUI's loading spinners and error alerts without writing that state machine by hand.

9. Process flows

Flow A — Register → verify email → login

User fills RegisterPage form (name, email, password) │ ▼ POST /api/auth/register │ ┌────┴─────┐ 409 200 OK { token, user, emailVerified: false } │ │ ▼ ▼ Show "email AuthContext.login(response) already taken" │ error inline ▼ Navigate to "/" (Dashboard) Show banner: "Verify your email — check your inbox" │ ▼ (separately) user opens the console-logged link: http://localhost:5173/verify-email?token=xxxx │ ▼ VerifyEmailPage calls GET /api/auth/verify-email?token=xxxx on mount │ ┌────┴────┐ 200 400 │ │ ▼ ▼ "Email verified!" "Invalid or expired link" link to /login

Flow B — Login → protected route

User submits LoginPage form │ ▼ POST /api/auth/login │ ┌────┴─────┐ 400 200 OK { token, user } │ │ ▼ ▼ Show "Invalid AuthContext.login(response) email or │ password" inline ▼ Navigate to "/" (Dashboard) │ ▼ ProtectedRoute checks AuthContext.token │ ┌─────┴─────┐ present missing │ │ ▼ ▼ Render Dashboard Redirect to /login

Flow C — Forgot password → reset password

User submits email on ForgotPasswordPage │ ▼ POST /api/auth/forgot-password │ ▼ ALWAYS shows the same message: "If that email is registered, a reset link has been sent" │ ▼ (separately) user opens the console-logged link: http://localhost:5173/reset-password?token=xxxx │ ▼ ResetPasswordPage reads token from URL, user submits new password │ ▼ POST /api/auth/reset-password { token, newPassword } │ ┌────┴─────┐ 400 200 OK │ │ ▼ ▼ "Invalid or "Password reset — please log in" expired link" Navigate to /login

Flow D — Expired/invalid token during normal use

User is on the Dashboard, JWT has expired (24h passed) │ ▼ Any API call fires, backend returns 401 │ ▼ axios response interceptor catches the 401 │ ▼ AuthContext.logout() — clears user+token from memory │ ▼ Redirect to /login (no silent refresh yet — refresh tokens are deferred, same as documented in the backend auth plan)

10. Error handling & UX conventions

  • Every backend error response is { "message": "..." } (from AuthExceptionHandler) — so every form can display error.response.data.message directly in an MUI Alert, with no per-endpoint special-casing needed.
  • Forgot password never shows a different message for a real vs. fake email — the frontend must not "improve" this by trying to hint whether the email existed; that would undo the backend's anti-enumeration protection.
  • Form submission buttons disable + show a spinner while a useMutation is isPending, using MUI's LoadingButton pattern.

11. Environment configuration

A .env file at the root of mycompass-ui:

VITE_API_BASE_URL=http://localhost:8080

Read in code via import.meta.env.VITE_API_BASE_URL — keeps the backend URL out of hardcoded strings, so pointing at a different environment later is a one-line change.

13. Explicitly deferred

  • Task/Project/Category pages — no backend for these yet
  • Silent token refresh — no refresh tokens on the backend yet (tracked in jwt-known-gaps.md)
  • Real design polish/branding — placeholder MUI defaults are fine until the core flows are proven end-to-end
  • Frontend automated tests (Vitest/React Testing Library) — reasonable next step once these pages exist, not before
