1. Where this fits in the domain design

This plan directly builds on decisions already locked in LifeOS_Domain_Design_QA.md:

Q2 — Personal vs collaboration: Personal-first. The auth system only needs to support single-owner accounts right now — no organizations, teams, or shared logins yet.
Q18 — Task ownership: Every Task has a createdBy → User. This means the User entity we're building here is the foundation every other domain entity will eventually reference. Getting the User model right now avoids a painful migration later.
Set G — Authentication & Users: Lists registration, login, password hashing, JWT/session approach, refresh tokens, email verification, password reset, roles as topics. This document answers the first four now and explicitly defers the rest (see §12).
Set K philosophy: "Domain model first, API second, database third." So we design the User entity and auth flow conceptually before writing a single endpoint.

3. Data model changes

A new User entity, designed to support both login methods from day one so we don't have to migrate later:

User
├── id                UUID / Long, primary key
├── email             unique, not null
├── passwordHash      nullable   ← null for Google-only accounts
├── name
├── provider           enum: LOCAL, GOOGLE
├── googleId           nullable, unique when present
├── createdAt
└── updatedAt
Why passwordHash is nullable: a user who only ever signs in with Google never sets a password, so it must be optional. provider tells us which login path is valid for that account, preventing someone from trying to password-login into a Google-only account.

4. High-level architecture

┌──────────────┐ Bearer JWT ┌───────────────────┐ JPA ┌────────────────┐ │ React UI │ ────────────────────────▶ │ Spring Boot API │ ─────────────────▶│ PostgreSQL │ │ (mycompass- │ ◀──────────────────────── │ (mycompass- │ ◀─────────────────│ (Docker) │ │ ui) │ JSON responses │ backend) │ │ │ └──────────────┘ └───────────────────┘ │ │ │ Google ID token (from popup) │ verifies token signature ▼ ▼ ┌──────────────┐ ┌───────────────────┐ │ Google │ │ Google's public │ │ Identity │ ────────────────────────▶ │ keys (JWKS) │ │ Services │ │ used to verify │ └──────────────┘ └───────────────────┘

Key idea: the frontend never talks to Google's servers for verification — it only gets a signed token from the Google popup and hands it to our backend. Our backend is the only thing that verifies it, using Google's published public keys.

6. Process flows

Flow A — Register with email/password

User fills registration form (email, password, name) │ ▼ POST /api/auth/register │ ▼ AuthController → is email already taken? │ ┌────┴────┐ yes no │ │ ▼ ▼ 409 Conflict Hash password (BCrypt) │ ▼ Save User(provider = LOCAL) │ ▼ JwtService generates app JWT │ ▼ Return { token, user } │ ▼ Frontend stores token in memory, redirects to dashboard

Flow B — Login with email/password

User submits { email, password } │ ▼ POST /api/auth/login │ ▼ Load User by email │ ┌────┴─────────────────┐ not found found, provider = LOCAL │ │ ▼ ▼ 401 Unauthorized BCrypt.matches(password, passwordHash)? │ ┌─────┴─────┐ yes no │ │ ▼ ▼ Generate JWT 401 Unauthorized │ ▼ Return { token, user }

Flow C — Sign in with Google

User clicks "Sign in with Google" (React button) │ ▼ Google Identity Services popup — user authenticates directly with Google │ ▼ Google returns a SIGNED ID TOKEN to the frontend (our app never sees the user's Google password) │ ▼ Frontend: POST /api/auth/google { idToken } │ ▼ Backend: GoogleTokenVerifier checks — • signature is genuinely from Google • audience matches OUR client ID • token has not expired │ ┌────┴─────┐ invalid valid → extract email, name, googleId │ │ ▼ ▼ 401 Does a User with this email already exist? │ ┌──────┴───────┐ yes no │ │ ▼ ▼ link googleId create new User if not already (provider = GOOGLE) linked │ │ └───────┬────────┘ ▼ JwtService generates OUR app JWT │ ▼ Return { token, user }

Flow D — Any authenticated request afterwards

Frontend makes an API call (e.g. GET /api/tasks) │ ▼ axios interceptor attaches: Authorization: Bearer <app JWT> │ ▼ JwtAuthenticationFilter intercepts the request │ ▼ Parse token, validate signature + expiry │ ┌────┴─────┐ invalid valid │ │ ▼ ▼ 401 Load user identity → set Spring SecurityContext │ ▼ Request proceeds to the real controller (e.g. TaskController)

7. JWT structure

Our own app-issued token (not Google's) carries just enough to identify the user:

{
  "sub": "<userId>",
  "email": "user@example.com",
  "iat": 1234567890,
  "exp": 1234654290
}
  • Signing algorithm: HS256, using jjwt (already added to pom.xml)
  • Secret: stored in application.properties for now (local dev only) — must move to an environment variable before any real deployment
  • Expiry: a single access token, e.g. 24h, for the MVP — no refresh token yet (see §12); when it expires, the user simply logs in again

8. Frontend components to build

ComponentResponsibility
AuthContext (React context)Holds the current user + JWT in memory only (React state) — never localStorage, to avoid XSS token theft
Configured axios instanceInterceptor that attaches Authorization: Bearer <token> to every request automatically
LoginPageMUI form (email/password) + the Google Sign-In button (@react-oauth/google)
RegisterPageMUI form for new local accounts
ProtectedRouteWraps routes that require login; redirects to /login if there's no valid token in context
MVP tradeoff: storing the token only in memory means a page refresh logs the user out (no persisted session). That's an accepted, intentional MVP limitation — solving it properly means adding refresh tokens (deferred, §12), not falling back to localStorage, which would reopen the XSS risk.

9. Security considerations

  • Password hashing: BCrypt via Spring Security's PasswordEncoder — never store or log plaintext passwords.
  • Token storage: in-memory (React state) only, per the tradeoff above.
  • CORS: already configured to allow http://localhost:5173 (see the Docker/Postgres doc's sibling setup).
  • Google token verification must happen server-side. Never trust a client-decoded JWT payload for authorization decisions — always re-verify signature and audience on the backend.
  • HTTPS: not required locally, but mandatory before any real deployment — JWTs sent over plain HTTP can be intercepted.

10. Implementation order

  1. Backend: User entity + Flyway migration
  2. Backend: PasswordEncoder bean + JwtService
  3. Backend: AuthController (register + login) + JwtAuthenticationFilter + updated SecurityConfig
  4. Verify via Swagger UI / curl — register, login, hit a protected endpoint with the token
  5. Backend: GoogleTokenVerifier + /api/auth/google endpoint
  6. Frontend: AuthContext + configured axios instance
  7. Frontend: LoginPage + RegisterPage (MUI)
  8. Frontend: wire up the Google Sign-In button
  9. Frontend: ProtectedRoute + redirect logic
  10. End-to-end test: register → login → access a protected route → sign out → sign in with Google

12. Explicitly deferred (per Set G)

Consistent with principle 3.4 in the domain doc ("don't over-engineer the MVP"), these are acknowledged but intentionally not built yet:

  • Refresh tokens / silent session renewal
  • Email verification on registration
  • Password reset ("forgot password") flow
  • Roles / permissions system beyond a single implicit user role
  • Account deletion
  • Rate limiting or brute-force protection on the login endpoint

Each of these can be added later without reworking the core User model or JWT approach designed here — they're additive, not architectural changes.
