1. Where this fits in the domain design

This plan directly builds on decisions already locked in LifeOS_Domain_Design_QA.md:

Q2 — Personal vs collaboration: Personal-first. The auth system only needs to support single-owner accounts right now — no organizations, teams, or shared logins yet.
Q18 — Task ownership: Every Task has a createdBy → User. This means the User entity we're building here is the foundation every other domain entity will eventually reference. Getting the User model right now avoids a painful migration later.
Set G — Authentication & Users: Lists registration, login, password hashing, JWT/session approach, refresh tokens, email verification, password reset, roles as topics. This document answers the first four now and explicitly defers the rest (see §12).
Set K philosophy: "Domain model first, API second, database third." So we design the User entity and auth flow conceptually before writing a single endpoint.

3. Data model changes IMPLEMENTED

The User entity, designed to support both login methods from day one so we don't have to migrate later:

User
├── id                UUID, primary key
├── email             unique, not null
├── passwordHash      nullable   ← null for Google-only accounts
├── name
├── provider           enum: LOCAL, GOOGLE
├── googleId           nullable, unique when present
├── emailVerified      boolean, default false
├── createdAt
└── updatedAt
Why passwordHash is nullable: a user who only ever signs in with Google never sets a password, so it must be optional. provider tells us which login path is valid for that account, preventing someone from trying to password-login into a Google-only account.

A second entity, VerificationToken, backs both email verification and password reset with one shared table instead of duplicating near-identical schema for each:

VerificationToken
├── id            UUID, primary key
├── token         unique random string (sent in the email link)
├── user          → User (many-to-one)
├── type          enum: EMAIL_VERIFICATION, PASSWORD_RESET
├── expiresAt     24h for verification, 1h for password reset
├── usedAt        nullable ← set once the token is consumed, makes it single-use
└── createdAt
Why one shared table instead of two: both features need the exact same shape — a random token tied to a user, with an expiry and single-use semantics. The type column is the only thing that differs, so one table (and one isValid() check: usedAt == null && expiresAt.isAfter(now)) covers both.

4. High-level architecture

┌──────────────┐ Bearer JWT ┌───────────────────┐ JPA ┌────────────────┐ │ React UI │ ────────────────────────▶ │ Spring Boot API │ ─────────────────▶│ PostgreSQL │ │ (mycompass- │ ◀──────────────────────── │ (mycompass- │ ◀─────────────────│ (Docker) │ │ ui) │ JSON responses │ backend) │ │ │ └──────────────┘ └───────────────────┘ │ │ │ Google ID token (from popup) │ verifies token signature ▼ ▼ ┌──────────────┐ ┌───────────────────┐ │ Google │ │ Google's public │ │ Identity │ ────────────────────────▶ │ keys (JWKS) │ │ Services │ │ used to verify │ └──────────────┘ └───────────────────┘

Key idea: the frontend never talks to Google's servers for verification — it only gets a signed token from the Google popup and hands it to our backend. Our backend is the only thing that verifies it, using Google's published public keys.

6. Process flows

Flow A — Register with email/password IMPLEMENTED

User fills registration form (email, password, name) │ ▼ POST /api/auth/register │ ▼ AuthController → is email already taken? │ ┌────┴────┐ yes no │ │ ▼ ▼ 409 Conflict Hash password (BCrypt) │ ▼ Save User(provider = LOCAL, emailVerified = false) │ ▼ Create VerificationToken(type = EMAIL_VERIFICATION, expires in 24h) │ ▼ EmailService "sends" the verification link (console-logged for now) │ ▼ JwtService generates app JWT │ ▼ Return { token, user, emailVerified: false } │ ▼ Frontend stores token in memory, redirects to dashboard (can show a "verify your email" banner since emailVerified is false)

Flow B — Login with email/password IMPLEMENTED

User submits { email, password } │ ▼ POST /api/auth/login │ ▼ Load User by email │ ┌────┴─────────────────┐ not found found, provider = LOCAL │ │ ▼ ▼ 401 Unauthorized BCrypt.matches(password, passwordHash)? │ ┌─────┴─────┐ yes no │ │ ▼ ▼ Generate JWT 401 Unauthorized │ ▼ Return { token, user }

Flow C — Sign in with Google IMPLEMENTED

User clicks "Sign in with Google" (React button — frontend not built yet) │ ▼ Google Identity Services popup — user authenticates directly with Google │ ▼ Google returns a SIGNED ID TOKEN to the frontend (our app never sees the user's Google password) │ ▼ Frontend: POST /api/auth/google { idToken } │ ▼ Backend: GoogleTokenVerifier checks — • signature is genuinely from Google • audience matches OUR client ID (app.google.client-id) • token has not expired │ ┌────┴─────┐ invalid valid → extract googleId (sub), email, name │ │ ▼ ▼ 400 Does a User with this email already exist? │ ┌──────┴───────────────┐ yes no │ │ ▼ ▼ Link googleId if Create new User not already set — (provider = GOOGLE, PROVIDER STAYS AS-IS emailVerified = true — → a LOCAL account Google already verified keeps its password AND this email address, gains Google as an so our own verification alternate sign-in flow is skipped entirely) method (hybrid account) │ │ └───────────┬───────────┘ ▼ JwtService generates OUR app JWT │ ▼ Return { token, user }
Two decisions worth noting, settled during implementation:
  • Linking never overwrites an existing googleId — if an account somehow already has one linked, a second Google sign-in with a different Google account's token does not silently replace it.
  • A brand-new Google signup skips email verification entirely (emailVerified = true immediately) — since Google itself already confirmed the user controls that email address, re-verifying it ourselves would be redundant.
Still required before this works end-to-end: a real Google OAuth Client ID from Google Cloud Console, set as app.google.client-id in application.properties (currently a placeholder). Without it, GoogleTokenVerifier will reject every token as having the wrong audience. This is an external setup step, not a code change.

Flow D — Any authenticated request afterwards IMPLEMENTED

Frontend makes an API call (e.g. GET /api/tasks) │ ▼ axios interceptor attaches: Authorization: Bearer <app JWT> │ ▼ JwtAuthenticationFilter intercepts the request │ ▼ Parse token, validate signature + expiry │ ┌────┴─────┐ invalid valid │ │ ▼ ▼ 401 Load user identity → set Spring SecurityContext │ ▼ Request proceeds to the real controller (e.g. TaskController)

Verified live: a request to a non-auth path with no token returns 403; Swagger's own paths stay open without one.

Flow E — Email verification IMPLEMENTED

User clicks the verification link from their email (…/verify-email?token=xxxx) │ ▼ Frontend calls GET /api/auth/verify-email?token=xxxx │ ▼ Look up VerificationToken by (token, type = EMAIL_VERIFICATION) │ ┌────┴──────────────────────┐ not found / expired / used found and valid │ │ ▼ ▼ 400 Bad Request user.emailVerified = true token.usedAt = now ← makes it single-use │ ▼ Return { message: "Email verified successfully" }
Verified live: registering issues a real 24h token, console-logs the link, and hitting it flips emailVerified from false to true on the very next login response.

Flow F — Forgot password → reset password IMPLEMENTED

User submits { email } on a "Forgot password?" form │ ▼ POST /api/auth/forgot-password │ ▼ Look up User by email, filter to provider = LOCAL │ ┌────┴─────────────────────────┐ not found / Google account found │ │ ▼ ▼ (do nothing) Create VerificationToken(type = PASSWORD_RESET, expires in 1h) │ │ │ ▼ │ EmailService "sends" the reset link │ │ └─────────────┬─────────────────────┘ ▼ Return the SAME message either way: "If that email is registered, a password reset link has been sent" (never reveals whether the email exists — prevents user enumeration) ────────────────────────────────────────────────────────────── User clicks the reset link, submits { token, newPassword } │ ▼ POST /api/auth/reset-password │ ▼ Look up VerificationToken by (token, type = PASSWORD_RESET) │ ┌────┴──────────────────────┐ not found / expired / used found and valid │ │ ▼ ▼ 400 Bad Request user.passwordHash = BCrypt(newPassword) token.usedAt = now ← single-use, can't be replayed │ ▼ Return { message: "Password reset successfully" }
Verified live, including the edge cases that matter for security:
  • Requesting a reset for a real email and a made-up email return byte-for-byte identical responses.
  • After reset, the old password is rejected (400) and the new one logs in successfully.
  • Replaying the same reset token a second time is rejected (400) — confirmed the token is genuinely single-use.

7. JWT structure

Our own app-issued token (not Google's) carries just enough to identify the user:

{
  "sub": "<userId>",
  "email": "user@example.com",
  "iat": 1234567890,
  "exp": 1234654290
}
  • Signing algorithm: HS256, using jjwt (already added to pom.xml)
  • Secret: stored in application.properties for now (local dev only) — must move to an environment variable before any real deployment
  • Expiry: a single access token, e.g. 24h, for the MVP — no refresh token yet (see §12); when it expires, the user simply logs in again

8. Frontend components to build

ComponentResponsibility
AuthContext (React context)Holds the current user + JWT in memory only (React state) — never localStorage, to avoid XSS token theft
Configured axios instanceInterceptor that attaches Authorization: Bearer <token> to every request automatically
LoginPageMUI form (email/password) + the Google Sign-In button (@react-oauth/google)
RegisterPageMUI form for new local accounts
ProtectedRouteWraps routes that require login; redirects to /login if there's no valid token in context
MVP tradeoff: storing the token only in memory means a page refresh logs the user out (no persisted session). That's an accepted, intentional MVP limitation — solving it properly means adding refresh tokens (deferred, §12), not falling back to localStorage, which would reopen the XSS risk.

9. Security considerations

  • Password hashing: BCrypt via Spring Security's PasswordEncoder — never store or log plaintext passwords.
  • Token storage: in-memory (React state) only, per the tradeoff above.
  • CORS: already configured to allow http://localhost:5173 (see the Docker/Postgres doc's sibling setup).
  • Google token verification must happen server-side. Never trust a client-decoded JWT payload for authorization decisions — always re-verify signature and audience on the backend.
  • HTTPS: not required locally, but mandatory before any real deployment — JWTs sent over plain HTTP can be intercepted.

12. Explicitly deferred (per Set G)

Email verification, password reset, and Google sign-in — originally listed here — are now all built (see Flows C, E, and F above). What's still intentionally deferred, consistent with principle 3.4 in the domain doc ("don't over-engineer the MVP"):

  • Refresh tokens / silent session renewal
  • Roles / permissions system beyond a single implicit user role
  • Account deletion
  • Rate limiting or brute-force protection on the login/forgot-password endpoints
  • Real email delivery — currently logs to the console via ConsoleEmailService instead of actually sending mail; swapping in a real EmailService implementation (e.g. JavaMailSender + a provider) won't require touching AuthService

Each of these can be added later without reworking the core User/VerificationToken model or JWT approach built here — they're additive, not architectural changes.
